# ۰۲ — چندمستأجری و مسیر مارکت‌پلیس

---

## تصمیم: یک دیتابیس مشترک با ستون `salon_id`

| گزینه | چرا نه |
|---|---|
| دیتابیس جدا به ازای هر سالن | **جستجوی سراسری فاز ۴ غیرممکن می‌شود.** «آرایشگاه‌های نزدیک من با کمترین انتظار» یعنی پرس‌وجو روی ۷۰۰ دیتابیس. مهاجرت‌ها هم کابوس می‌شوند |
| اسکیمای جدا در یک دیتابیس | همان مشکل، با پیچیدگی بیشتر در MySQL |
| **یک دیتابیس، ستون `salon_id`** ✅ | جستجوی بین‌سالنی یک `WHERE` است. مهاجرت یک بار اجرا می‌شود. پشتیبان‌گیری ساده است |

**هزینه‌ای که می‌پذیریم:** جداسازی داده به انضباط کد وابسته است، نه به مرز فیزیکی دیتابیس. پس
باید **چندلایه** دفاع کنیم — بخش بعد.

ثبت رسمی: [ADR-0001](adr/0001-single-database-multitenancy.md)

## دفاع چندلایه از جداسازی داده

یک لایه کافی نیست. سه لایه:

### لایه ۱ — اسکوپ سراسری خودکار

```php
// app/Domain/Tenancy/Concerns/BelongsToSalon.php
trait BelongsToSalon
{
    protected static function bootBelongsToSalon(): void
    {
        static::addGlobalScope(new SalonScope());

        static::creating(function ($model) {
            $model->salon_id ??= Tenancy::salonIdOrFail();
        });
    }
}
```

هر مدلِ متعلق به سالن این trait را دارد. فراموش کردنش، تنها راه نشت است — پس:

### لایه ۲ — آزمون معماری که فراموشی را می‌گیرد

```php
// tests/Architecture/TenancyTest.php
test('هر مدل دارای ستون salon_id باید trait را داشته باشد', function () {
    foreach (allTenantTables() as $table) {   // شبه‌کد — پیاده‌سازی: TenantRequired + محدودسازی دستی هر کوئری
        if (Schema::hasColumn($model->getTable(), 'salon_id')) {
            expect(class_uses_recursive($model))->toContain(BelongsToSalon::class);
        }
    }
});
```

این تست در CI اجرا می‌شود. هیچ مدلی نمی‌تواند بی‌اسکوپ وارد شود.

### لایه ۳ — اجبار در سطح دیتابیس

هر کلید خارجی **مرکب** است، نه ساده:

```sql
-- به‌جای: FOREIGN KEY (customer_id) REFERENCES customers(id)
UNIQUE KEY uk_customers_salon (id, salon_id),
FOREIGN KEY (customer_id, salon_id) REFERENCES customers(id, salon_id)
```

این یعنی حتی یک باگ در کد هم **نمی‌تواند** نوبتِ سالن A را به مشتریِ سالن B وصل کند. دیتابیس
اجازه نمی‌دهد. کمی سربار دارد، ولی در برابر [R9](../00-product/09-risks.md) ارزشش را دارد.

## تشخیص مستأجر

به ترتیب اولویت:

| مسیر | نمونه | کاربرد |
|---|---|---|
| زیردامنه | `shahab.reshen.ir` | صفحهٔ عمومی سالن (نام مستعار) |
| **مسیر** ✅ | `reshen.ir/s/shahab` | **قانونی (canonical)** |
| نشست کاربر | `/panel/*` | پنل — از `salon_id` کاربر واردشده |
| هدر | `X-Salon-Id` | API اپ |

**چرا مسیر، قانونی است و نه زیردامنه:** در فاز ۴ همهٔ اعتبار سئو باید روی یک دامنه جمع شود.
`reshen.ir/s/tehran/shahab` به رتبهٔ `reshen.ir` کمک می‌کند؛ `shahab.reshen.ir` نمی‌کند. ضمناً
SSL وایلدکارت روی هاستینگ ایرانی همیشه بی‌دردسر نیست.

زیردامنه به‌عنوان نام مستعار با ریدایرکت ۳۰۱ به مسیر قانونی پشتیبانی می‌شود.

ثبت رسمی: [ADR-0002](adr/0002-path-based-tenant-routing.md)

## جدول‌های سراسری (بدون `salon_id`)

| جدول | چرا سراسری |
|---|---|
| `users` | یک شمارهٔ موبایل = یک هویت در کل پلتفرم. لازمهٔ فاز ۴ |
| `salons` | خودِ مستأجر |

| `plans`, `platform_subscriptions`, `platform_invoices` | صورتحساب خودِ ما |

## `users` در برابر `customers` — تفکیک حیاتی

این ظریف‌ترین تصمیم مدل داده است و مستقیماً فاز ۴ را ممکن یا غیرممکن می‌کند:

```
users (سراسری)                     customers (به ازای هر سالن)
┌────────────────────┐             ┌──────────────────────────────┐
│ id                 │◀───────┐    │ id                           │
│ phone (یکتا سراسری)│        └────│ user_id (nullable)           │
│ name               │             │ salon_id                     │
│ created_at         │             │ name, notes, trust_score     │
└────────────────────┘             │ hair_notes, clipper_size     │
                                   │ visit_count, last_visit_at   │
   یک هویت در کل پلتفرم           │ preferred_staff_id           │
                                   └──────────────────────────────┘
                                      پروندهٔ مشتری در هر سالن، جدا
```

**قواعد:**
- «امیر» در سالن A و سالن B، **دو ردیف `customers`** دارد ولی **یک ردیف `users`**
- سالن A **هرگز** پروندهٔ امیر در سالن B را نمی‌بیند — نه در کد، نه در API، نه در گزارش
- `user_id` می‌تواند `null` باشد: مشتری حضوریِ بی‌شماره
- وقتی مشتری با موبایلش وارد می‌شود، فقط سالن‌هایی را می‌بیند که **خودش** در آن‌ها نوبت گرفته

**چرا این تفکیک لازم است:** در فاز ۴، اپ مشتری باید بگوید «سابقهٔ نوبت‌های تو در همهٔ آرایشگاه‌ها»
— که نیازمند هویت سراسری است. ولی هم‌زمان سالن A نباید بفهمد مشتری‌اش جای دیگر هم می‌رود. بدون
این تفکیک، یا فاز ۴ غیرممکن است یا [R4](../00-product/09-risks.md) اتفاق می‌افتد.

## اجرای فنیِ «قرارداد عدم‌واسطه‌گری»

وعدهٔ [۰۶ §۹](../00-product/06-pricing-business-model.md) باید کد باشد، نه فقط بند قرارداد:

```php
// app/Domain/Tenancy/Rules/NonSolicitation.php
// در فاز ۴: یک شماره که در سالنی مشتری ثبت‌شده است،
// هرگز در نتایج تبلیغاتی یا پیشنهاد سالن رقیب ظاهر نمی‌شود.
final class NonSolicitation
{
    /** سالن‌هایی که این شماره در آن‌ها مشتری ثبت‌شده است. */
    public function protectedSalonIds(string $phone): array;

    /** آیا سالن X مجاز است این شماره را در کمپین هدف بگیرد؟ */
    public function mayTarget(int $salonId, string $phone): bool;
}
```

و یک آزمون که هرگز حذف نمی‌شود:

```php
test('سالن نمی‌تواند مشتری ثبت‌شدهٔ سالن دیگر را هدف کمپین کند', ...);
```

## ورود پشتیبانی به حساب سالن

تیم ما باید بتواند برای پشتیبانی وارد شود، ولی:

- فقط نقش `platform_admin`
- **همیشه** در `audit_logs` ثبت می‌شود (چه کسی، چه سالنی، کِی، چه دید)
- به سالن اطلاع داده می‌شود
- دسترسی فقط خواندنی مگر با تأیید صریح صاحب سالن
- نشست حداکثر ۳۰ دقیقه

## آمادگی برای مقیاس

اگر روزی یک سالن خیلی بزرگ شد یا کل سیستم سنگین شد:

| مرحله | کار |
|---|---|
| ۱ | رپلیکای خواندنی برای گزارش‌ها و جستجو |
| ۲ | پارتیشن‌بندی `appointments` بر اساس ماه |
| ۳ | انتقال دادهٔ سرد (بیش از ۲ سال) به جدول آرشیو |
| ۴ | فقط در صورت لزوم: شاردینگ بر اساس `salon_id` — چون `salon_id` همه‌جا هست، این ممکن می‌ماند |

قدم ۴ احتمالاً هرگز لازم نمی‌شود. ولی چون از روز اول `salon_id` را همه‌جا داریم، در را باز نگه داشته‌ایم.
