# ۰۴ — موتور صف زنده و ETA

> **دربارهٔ قطعه‌کدهای این سند:** این‌ها شبه‌کدِ دورهٔ طراحی‌اند و با
> فرض ORM نوشته شده‌اند. پیاده‌سازی واقعی PHP خام است و از مخزن‌ها
> استفاده می‌کند، ولی *قاعده‌ها* همان‌اند. بالای هر قطعه نوشته شده
> کدام فایل واقعاً این کار را می‌کند.


> مشخصات فنی [فیچر اصلی](../00-product/04-core-feature.md). اگر فقط یک بخش از این پروژه قرار است

## ۱. مسئله در یک جمله

با داشتن: صندلی‌ها، کسانی که رزرو کرده‌اند، کسانی که سرزده آمده‌اند، و اینکه الان چه کسی روی
صندلی است —
**بگو هر نفر تقریباً چه ساعتی روی صندلی می‌نشیند، و آن‌قدر درست بگو که مشتری باورت کند.**

## ۲. قواعد ترتیب صف

هر صندلی (آرایشگر) صف مستقل خودش را دارد.

```
اولویت ۱:  روی صندلی (status = in_chair)             ← حداکثر یک نفر
اولویت ۲:  رزروشده و «در پنجرهٔ حق تقدم»
اولویت ۳:  بقیه، به ترتیب زمان ورود به صف (queued_at)
```

### پنجرهٔ حق تقدم

نوبت رزروشده از **۱۰ دقیقه قبل** تا **۱۰ دقیقه بعدِ** `scheduled_at` بر حضوری‌ها مقدم است.
بیرون از این پنجره، به ترتیب زمان ورود برمی‌گردد.

| چرا این قاعده | |
|---|---|
| **عادلانه است** | کسی که رزرو کرده، حقش محفوظ است — ولی اگر ۴۰ دقیقه دیر بیاید، جلوی کسی که نیم ساعت نشسته نمی‌افتد |
| **قابل فهم است** | مشتریِ منتظر که می‌بیند یکی از راه رسید و جلویش افتاد، توضیح ساده‌ای می‌خواهد. «ایشون ساعت ۶ نوبت داشت» کافی است |
| **قابل تنظیم است** | `salons.settings.priority_window_minutes` — هر سالن فرهنگ خودش را دارد |

```php
// شبه‌کد طراحی. پیاده‌سازی واقعی: app/Domain/Queue/QueueOrderingService.php
private function sortKey(Appointment $a, CarbonInterface $now): array
{
    if ($a->status === Status::InChair) {
        return [0, 0];
    }

    if ($a->kind === Kind::Booked && $a->scheduled_at !== null) {
        $w = $this->salon->priorityWindowMinutes();   // پیش‌فرض ۱۰
        if ($a->scheduled_at->diffInMinutes($now, absolute: true) <= $w) {
            return [1, $a->scheduled_at->timestamp];
        }
    }

    return [2, $a->queued_at?->timestamp ?? $a->scheduled_at->timestamp];
}
```

## ۳. تخمین مدت خدمت

### گام ۱ — مدت پایه

به ترتیب، اولین موردی که موجود باشد:

| اولویت | منبع | شرط |
|---|---|---|
| ۱ | `duration_stats.p50_minutes` برای (آرایشگر × خدمت) | `sample_count >= 8` |
| ۲ | `staff_service.duration_minutes` | آرایشگر خودش تنظیم کرده |
| ۳ | `services.duration_minutes` | عدد اسمی سالن |
| ۴ | ۳۰ دقیقه | آخرین پناه |

> **چرا حداقل ۸ نمونه:** با کمتر از آن، میانه به یک روز عجیب حساس است — یک مشتری پرحرف، کل
> تخمین را خراب می‌کند. عدد ۸ تجربی است و در فاز ۲ با دادهٔ واقعی کالیبره می‌شود.

### گام ۲ — ضریب شخصی مشتری

بعضی‌ها همیشه بیشتر طول می‌کشند: حرف می‌زنند، نظرشان عوض می‌شود، موی سختی دارند.

```
customer.duration_factor = میانگین( مدت واقعی این مشتری ÷ p50 همان خدمت )
```

فقط با **حداقل ۳ مراجعه** فعال می‌شود و به `[۰٫۷ , ۱٫۵]` بریده می‌شود.

> بریدن بازه عمدی است. ضریب ۲٫۳ معمولاً یعنی یک نوبتِ اشتباه ثبت‌شده، نه یک مشتریِ واقعاً کند.
> یک داده‌ی پرت نباید تخمین همه را خراب کند.

### گام ۳ — چند خدمت

```
مدت کل = Σ مدت هر خدمت + (تعداد خدمات − ۱) × بافر_داخلی
```
`بافر_داخلی` پیش‌فرض ۲ دقیقه (عوض کردن ابزار).

### فرمول نهایی

```
expected_duration(نوبت) = round(
    Σ_خدمات base_duration(آرایشگر, خدمت) × clamp(customer.duration_factor, 0.7, 1.5)
    + (تعداد خدمات − ۱) × بافر_داخلی
)
```

## ۴. محاسبهٔ ETA

```
باقی‌ماندهٔ نفر روی صندلی:
    remaining = max(۲ , expected_duration(فعلی) − (اکنون − actual_start_at))

کف ۲ دقیقه عمدی است: هرگز نگو «همین الان» چون مشتری می‌دود و می‌آید و باز منتظر می‌ماند.

برای نفر iام در صف (از ۱):
    ETA(i) = اکنون + remaining + Σ_{j<i} ( expected_duration(j) + بافر_بین_مشتری )

کران بالای بازه — با p80 به‌جای p50:
    ETA_max(i) = اکنون + remaining_p80 + Σ_{j<i} ( expected_duration_p80(j) + بافر )
```

`بافر_بین_مشتری` = `salons.settings.turnover_buffer_minutes`، پیش‌فرض **۵ دقیقه** (جارو، تمیز کردن،
دست‌شویی، سیگار).

### نمایش — قاعده‌ای که شکسته نمی‌شود

> **هرگز یک عدد دقیق نشان نده. همیشه بازه.**

| موقعیت | نمایش |
|---|---|
| نفر بعدی | «نوبت بعدی توست» |
| کمتر از ۱۵ دقیقه | «حدود ۱۰ دقیقهٔ دیگر» |
| ۱۵ تا ۶۰ دقیقه | «۲۵ تا ۳۵ دقیقهٔ دیگر» |
| بیش از ۶۰ دقیقه | «حدود ساعت ۱۹:۳۰ تا ۱۹:۵۰» |
| بازهٔ بزرگ‌تر از ۲۵ دقیقه | به ۲۵ دقیقه محدود کن و علامت «تخمین تقریبی» بزن |

آخرین قاعده مهم است: بازهٔ «۳۰ تا ۹۰ دقیقه» به مشتری هیچ نمی‌گوید و فقط بی‌اعتمادی می‌سازد.
بهتر است بگوییم «حدود ۴۵ دقیقه، ممکن است بیشتر شود».

## ۵. زمان‌بندی محاسبهٔ مجدد

ETA وقتی دوباره حساب می‌شود که چیزی واقعاً عوض شده باشد:

| رویداد | کار |
|---|---|
| کسی به صف اضافه شد | محاسبهٔ مجدد صفِ همان آرایشگر |
| کسی «شروع» شد | محاسبهٔ مجدد |
| کسی «تمام شد» | محاسبهٔ مجدد + به‌روزرسانی `duration_stats` |
| لغو یا جابه‌جایی | محاسبهٔ مجدد |
| آرایشگر ترتیب را دستی عوض کرد | محاسبهٔ مجدد |
| **هر ۹۰ ثانیه، خودکار** | چون گذشتِ زمان خودش ETA را عوض می‌کند |

پس از هر محاسبه، رویداد `QueueRecalculated` منتشر می‌شود و شنونده‌ها تصمیم می‌گیرند پیامک لازم است یا نه.

## ۶. پیامک‌های صف

| پیامک | ماشه | ضدتکرار |
|---|---|---|
| **نوبتت نزدیکه** | ETA بین ۲۰ تا ۳۰ دقیقه رسید | `nearly_up_notified_at` |
| **صندلی آماده‌ست** | نفر بعدی شد | یک بار |
| **عقب افتادیم** | ETA بیش از ۲۰ دقیقه از تخمین قبلیِ ارسال‌شده عقب‌تر رفت | حداکثر یک بار در هر نوبت |
| **یادآور روز قبل** | ۲۴ و ۲ ساعت قبل از `scheduled_at` | `reminded_at` |

### قواعد ضدآزار

هیچ‌چیز به اندازهٔ پیامک زیاد، محصول را منفور نمی‌کند:

- حداکثر **۴ پیامک** به ازای هر نوبت
- هیچ پیامکی بین **۲۳:۰۰ تا ۸:۰۰** (مگر «صندلی آماده‌ست» که خودِ مشتری در صف است)
- «عقب افتادیم» فقط یک بار — بار دوم بدتر از سکوت است
- پیش از ارسال، موجودی کیف پیامک بررسی می‌شود ([۰۶ §۴](../00-product/06-pricing-business-model.md))
- پیامک‌های حیاتی حتی با موجودی منفی (تا ۱۰۰) ارسال می‌شوند

### متن‌ها

```
نوبتت نزدیکه:
{customer}، ۲ نفر جلوتری. حدود {eta} دیگه نوبتته.
{salon} — {barber}
reshen.ir/q/{token}

صندلی آماده‌ست:
{customer}، نوبتت شد. منتظرتیم.
{salon}

عقب افتادیم:
{customer} شرمنده، امروز شلوغ شد و حدود {delay} دقیقه عقبیم.
نوبتت حدود {new_eta} می‌شه.
{salon}
```

> **لحن عمداً انسانی است.** «مشترک گرامی، نوبت شما…» مثل پیامک بانک است و خوانده نمی‌شود. نام
> آرایشگر در پیامک، نرخ باز شدن لینک را بالا می‌برد چون مشتری با او رابطه دارد، نه با سالن.

## ۷. یادگیری: به‌روزرسانی `duration_stats`

با هر `AppointmentCompleted`:

```php
// شبه‌کد طراحی. پیاده‌سازی واقعی: app/Domain/Queue/DurationLearner.php
$actual = $appointment->actual_start_at->diffInMinutes($appointment->actual_end_at);

// ۱ — فیلتر دادهٔ پرت: کمتر از ۵ یا بیشتر از ۱۸۰ دقیقه، خطای ثبت است نه واقعیت
if ($actual < 5 || $actual > 180) {
    return;
}

// ۲ — فقط نوبت‌های تک‌خدمتی به آمار خدمت کمک می‌کنند
//     (در چندخدمتی نمی‌دانیم کدام خدمت چقدر طول کشید)
if ($appointment->items->count() === 1) {
    DurationStat::record(
        salonId:   $appointment->salon_id,
        staffId:   $appointment->staff_id,
        serviceId: $appointment->items->first()->service_id,
        minutes:   $actual,
    );
}

// ۳ — ضریب شخصی مشتری از کل نوبت به‌روز می‌شود
$appointment->customer?->updateDurationFactor($actual, $appointment->expected_duration_minutes);
```

**محاسبهٔ صدک‌ها:** یک کار شبانه، از **۲۰۰ نمونهٔ آخر** هر ترکیب (آرایشگر × خدمت). پنجرهٔ متحرک
عمدی است — آرایشگر با تجربه سریع‌تر می‌شود و آمار باید همراهش بیاید، نه اینکه در دادهٔ دو سال پیش
گیر کند.

## ۸. حالت‌های خاص

| حالت | رفتار |
|---|---|
| آرایشگر «شروع» نزد | با ثبت «تمام شد» نفر قبلی، نفر بعدی خودکار `in_chair` می‌شود |
| آرایشگر «تمام شد» نزد | پس از `۲ × expected_duration`، هشدار در پنل: «هنوز مشغولی؟» — آمار به‌روز نمی‌شود |
| مشتری نیامد | «رد شد» → به انتهای صف یا `no_show` (پس از ۱۵ دقیقه) |
| آرایشگر وسط روز رفت | صفش به آرایشگرهای دیگر پیشنهاد می‌شود (فاز ۳: A22) |
| سالن بست و صف خالی نشد | کار شبانه همه را `no_show` می‌کند و به مدیر گزارش می‌دهد |
| `staff_id = null` | ETA = کمترین ETA میان آرایشگرهای واجد شرایط |
| دو نفر هم‌زمان ثبت شدند | `queued_at` با دقت میکروثانیه؛ در تساوی، `id` کوچک‌تر |
| ساعت کاری تمام شد | ETA بعد از پایان ساعت کاری ⇒ «امروز نمی‌رسیم» و پیشنهاد فردا |

## ۹. عملکرد

کوئری صف، داغ‌ترین کوئری کل سیستم است (هر ۱۵ ثانیه، به ازای هر کاربر باز).

| تکنیک | |
|---|---|
| کش صف در Redis، کلید `queue:{salon}:{staff}`، TTL ۳۰ ثانیه | |
| باطل‌سازی با رویداد، نه با انقضا | |
| `duration_stats` در کش با TTL یک ساعت | تغییرات کند است |
| پاسخ API با **ETag**؛ بدون تغییر ⇒ `304` | اکثر پولینگ‌ها چیزی عوض نکرده‌اند |
| ایندکس `(salon_id, staff_id, status, queued_at)` | |
| محاسبه در حافظه، نه در SQL | صف معمولاً زیر ۲۰ ردیف است |

**هدف:** محاسبهٔ کامل صف یک سالن زیر **۵۰ میلی‌ثانیه**.

## ۱۱. آنچه عمداً نمی‌سازیم

| | چرا |
|---|---|
| مدل یادگیری ماشین | با کمتر از ۵۰ هزار نمونه، میانه از رگرسیون بهتر است و **قابل توضیح** هم هست. وقتی آرایشگر بپرسد «چرا ۳۵ دقیقه؟» باید جوابی داشته باشیم |
| پیش‌بینی ترافیک شهری | ارزشش را ندارد |
| بهینه‌سازی سراسری صف (چیدمان مجدد همه) | مشتری باید ترتیب را بفهمد. یک صف عادلانه و قابل توضیح، از یک صف بهینه و مرموز بهتر است |
| تخمین برای بیش از ۳ ساعت آینده | خطا آن‌قدر بالاست که بی‌معنی می‌شود. بعد از آن فقط `scheduled_at` نشان داده می‌شود |
